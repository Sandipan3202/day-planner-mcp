1. What is MCP?

MCP (Model Context Protocol) is a standard way for an AI app, like Claude Code, to connect to outside tools and data, like your calendar, a database or a file system.

A simple comparison: MCP is like a USB-C port for AI. Before USB-C, every device needed its own special cable. With USB-C, one plug shape works for everything. MCP does the same for AI apps and the services they use.

Without MCP

Every AI app writes its own custom code for every service. 3 apps × 4 services = 12 separate integrations to build and maintain.

With MCP

Each service builds one MCP server. Each AI app supports MCP once. Then any app can use any server. 3 + 4 = 7 pieces, not 12.

In one line: MCP lets Claude discover what a service can do, and then ask it to do those things, using a shared set of rules.

Under the hood, the messages are JSON-RPC 2.0: small JSON objects that say "call this method with these arguments" and get a JSON reply back. When we opened /mcp, it showed Protocol: 2026-07-28, the version of the MCP rules the two sides agreed to use.

3. What a server can offer: tools, resources, prompts

An MCP server can offer three kinds of things. They're called primitives.

PrimitiveThink of it asWho decides to use itExample
ToolAn action (a function the AI can call)The AI modelcreate_event, list_events
ResourceSome data to read, like a fileThe app or the userplanner://preferences (Phase 2)
PromptA ready-made instruction templateThe user (e.g. a slash command)plan_my_day (Phase 2)

The Google Calendar server offers only tools (9 of them). Your Phase 2 server, focus-planner, will offer all three, so you learn each one.

Each tool comes with a JSON Schema: a description of its inputs, saying which are required and which are optional, plus their types and defaults. Claude reads this to know how to call the tool. For example, create_event requires summary, startTime and endTime, and calendarId is optional (default: your main calendar).

4. How they talk: transports

A transport is the "road" the messages travel on. MCP has two main ones:

stdio (local)

The host starts the server as a program on your computer and talks to it through its input and output. No network and no sign-in needed. Phase 2 uses this.

Streamable HTTP (remote)

The server runs somewhere else on the internet and messages go over HTTP. Needs a sign-in (OAuth). Phase 1 used this.

5. Why Google Calendar, and why this connector?

  • Learn as a user before building. Using a finished server first shows what "good" looks like before you write your own in Phase 2.
  • Real data, real results. Your calendar is something you know well, so you can instantly tell if Claude got it right.
  • Covers reading and writing. Listing, creating, moving and deleting events exercises the most important kinds of tool.
  • Already available, and free. The connector comes with your claude.ai account. You only had to sign in through /mcp. No Google Cloud setup and no extra cost.
  • Sets up Phase 2. Your focus-planner server will not talk to Google. Calendar work stays with this server, and yours does the planning. Claude combines the two. That shows how MCP servers work together.

Decision D1: start with the built-in connector (fast, simple). Optionally try a self-hosted calendar server later, to learn how sign-in (OAuth) works in detail.

7. One request, up close

Here's exactly what happened when you asked "What's on my calendar tomorrow?"

  1. Claude decides which tool to useFrom the tool list, list_events fits best. "Tomorrow" becomes a time range: today is Oct 7 and your time zone is India (+05:30).
  2. The client sends the call 
    list_events {
  "startTime": "2026-10-08T00:00:00+05:30",
  "endTime":   "2026-10-09T00:00:00+05:30",
  "orderBy":   "startTime"
}
    No calendarId, so the server used your main calendar.
  3. The server replies with JSONAbout 15 fields per event: ID, start, end, title, creator, reminders, link, "transparency" and more. (Shortened here.) 
    { "summary": "MCP test-1",
  "start": { "dateTime": "2026-10-08T14:00:00+05:30" },
  "end":   { "dateTime": "2026-10-08T15:00:00+05:30" },
  "eventType": "DEFAULT", ... }
  4. Claude writes a short answerIt picks the few fields you care about (time and title) and shows them in a table. The rest is dropped.

Notice: the server returns lots of raw data and the model turns it into a short answer. That raw data still counts toward your Claude usage, so asking for a narrow time range is cheaper.

8. Key lessons from Phase 1

  • 1. The schema shapes behavior. Because calendarId is optional and defaults to your main calendar, a forgotten argument writes to the wrong place, silently.
  • 2. The server does no thinking. It didn't warn about overlapping events and didn't care that two events had the same name. Spotting clashes and asking "which one?" is the model's job.
  • 3. Names vs IDs. You speak in names ("MCP Test", "my test event"). Tools need IDs. So many tasks take two steps: find the ID, then act on it.
  • 4. Rules in chat don't last. Claude followed "test events go to MCP Test" only because it was in this conversation. To make a rule permanent, put it in a file, a resource or a prompt. That's a Phase 2 job.
  • 5. Read it back. A "success" reply only means it worked at that moment. The first test event was deleted 41 seconds later. Always check with a read.
  • 6. Missing details → ask before writing. For reads, a reasonable guess is fine. For writes (create, move, delete), Claude asked when the time, calendar or event was unclear.
  • 7. Not everything on a calendar is busy time. Google Tasks showed up as "focus time" events marked free. Your Phase 2 tool must ignore free events when finding open time.
  • 8. Hosted sign-in hides the details. You clicked "allow" in a browser, but the token is stored on claude.ai's side, not on your machine. To really learn OAuth, you'd self-host a server (optional Phase 1b).

9. Glossary

MCP
Model Context Protocol: a standard for connecting AI apps to tools and data.
Host
The AI app you use (Claude Code).
Client
The part of the host that connects to one MCP server.
Server
A program that offers tools, resources and/or prompts.
Tool
An action the AI can call, like create_event.
Resource
Read-only data the server shares, like a settings file.
Prompt
A reusable instruction template, often shown as a slash command.
JSON Schema
A description of a tool's inputs: names, types, required or optional, defaults.
Transport
How messages travel: stdio (local) or Streamable HTTP (remote).
JSON-RPC
The simple request/response message format MCP uses.
OAuth
A safe sign-in method: you approve access in a browser, and the app gets a token instead of your password.
Connector
claude.ai's name for an MCP server you add to your account.
calendarId
The unique ID of a calendar. The special value primary means your main calendar.

10. Ten interview questions

Try to answer each one out loud first, then open it to check.

Q1What is MCP, and what problem does it solve?

MCP (Model Context Protocol) is an open standard for connecting AI applications to external tools and data. It replaces one-off custom integrations, where every app × every service needs its own code, with one shared protocol. A service builds one MCP server, an app supports MCP once, and they work together.

Q2Explain host, client and server in MCP.

The host is the AI application the user interacts with (e.g. Claude Code). Inside it, an MCP client keeps a one-to-one connection with one MCP server. The server offers capabilities. A host can have many clients, one per server. In my project: Claude Code is the host, and Google's Calendar MCP server is a server.

Q3What are tools, resources and prompts? When would you use each?
  • Tools: actions the model decides to call (create an event, run a query). They can have side effects.
  • Resources: read-only data the application or user chooses to load as context (a config file, a document).
  • Prompts: reusable templates the user picks, often as slash commands, to start a workflow.

Rule of thumb: does something → tool; is something to read → resource; is a way of asking → prompt.

Q4What's the difference between the stdio and Streamable HTTP transports?

stdio: the host starts the server as a local process and exchanges messages through standard input and output. It's simple, fast, has no network and usually no auth, and suits local tools. Streamable HTTP: the server runs remotely and is reached over HTTP, which suits shared or hosted services. It needs proper authentication, usually OAuth. My Phase 1 calendar server was remote HTTP. My Phase 2 server will use stdio.

Q5How does the model know which tools exist and how to call them?

After connecting, the client asks the server for its tool list (tools/list). Each tool has a name, a description and an input JSON Schema. The host gives these to the model, which picks a tool and builds arguments that match the schema. The client then sends a tools/call request. Good descriptions and schemas directly improve how well the model uses the tool.

Q6How does authentication work for a remote MCP server compared with a local one?

Remote servers typically use OAuth: the user approves access in a browser, and the client gets a token to send with requests, never the user's password. In my case, claude.ai's connector proxy did the OAuth flow and held the token. Local stdio servers usually need no user sign-in. Any secrets (API keys) are passed through environment variables and kept out of git.

Q7A tool's calendarId is optional and defaults to the primary calendar. What's the risk, and how would you reduce it?

Risk: if the model forgets the argument, writes silently go to the user's real calendar. I saw that the only thing preventing it was conversation memory. Ways to reduce it: put the rule somewhere durable (a project instructions file, an MCP prompt or resource), have the model confirm the target before writes, verify with a read-back, or (if you own the server) make the field required or reject writes without it.

Q8The user says "move my test event" and two events match. Whose job is it to handle that, and how?

The model's (client side). The server just returns all matches. Titles aren't unique, only IDs are. The correct behavior is to search, notice more than one match, and ask the user which one, before calling any write tool. Guessing on a write is risky. That's what happened in my exercise E6.1.

Q9Why didn't the calendar server warn about overlapping events? Where should conflict checks live?

Google Calendar allows overlaps, and the server simply did what it was asked. MCP servers usually expose plain operations, not judgment. Conflict checks belong in the reasoning layer: the model calls a read tool first (list_events or suggest_time), or a dedicated tool computes free time. That's exactly the job of my Phase 2 tool, find_focus_blocks.

Q10How would you debug an MCP integration?
  • Check connection status, protocol version and capabilities (in Claude Code: /mcp).
  • Look at each tool call's actual arguments and raw result in the transcript.
  • Test the server on its own with the MCP Inspector: list and call tools, resources and prompts directly, without the model.
  • For stdio servers, log to stderr, never stdout, because stdout carries the protocol messages.
  • Verify writes with a read-back rather than trusting the success reply.
